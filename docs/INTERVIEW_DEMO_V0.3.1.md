# Bill System v0.3.1 面试演示手册

## 面试前

1. 打开 Docker Desktop，双击 `start.cmd`，等待七个容器健康。
2. 双击 `reset-demo.cmd`。
3. 双击 `verify-v0.3.1.cmd`，完成核心可靠性、三端联动与 Kafka 三层全量回归；面试当天不要首次下载镜像。
4. 浏览器准备三个标签：`/client`、`/operations`、`/database`。

## 90 秒主线

开场：

> 这是生活服务交易可靠性实验台，不是普通商城 CRUD。我保留同步下单路径，又增加 202、事务 Outbox 和真实 Kafka 的高峰入口，用可注入故障和自动 Gate 证明削峰、至少一次投递下的幂等，以及支付最终一致性。

操作：

1. 客户端点击“异步受理订单”，指出接口先返回 ACCEPTED，之后状态变为 SUCCEEDED。
2. 运维台点击“暂停消费”，再点“制造 12 个积压”，展示 Lag 和三个分区水位上升。
3. 点击“恢复消费”，展示 Lag 排空、Outbox 与请求状态收敛。
4. 选择一条成功消息并点“重复投递”，指出 received 增加而 businessExecutions 仍是 1。
5. 数据库台展示 `order_requests → outbox_events → kafka_deliveries → orders` 的真实记录。

收尾：

> Kafka 只把瞬时压力变成可观察的排队时间，不增加下游容量，也不解决跨库事务。数据库最终事实、业务幂等、补偿和对账仍然必须存在。本地是单 Broker，我不会把它说成生产高可用。

## 5 分钟深挖

### 0:00–1:00 同步与异步取舍

- 同步路径立即返回业务结果，适合用户必须马上知道库存结果的普通流量。
- 异步路径立即返回受理结果，适合峰值流量，代价是客户端管理处理中状态。
- 强调 202 延迟和最终完成延迟是两个指标，不能混报。

### 1:00–2:30 Outbox 与重复消息

- 创建请求与 Outbox 在同一数据库事务，避免“订单受理了、消息丢了”。
- Relay 发布后才写 PUBLISHED、Partition 和 Offset。
- 发布成功后进程宕机可能造成重复；点“重复投递”，用 `receivedCount > businessExecutions` 证明消费者幂等。

### 2:30–3:40 Lag 与削峰

- 暂停消费者、制造积压，解释 `Lag = LEO - committed offset`。
- 恢复消费者后观察 Lag 归零；三个 Partition 对应三个并发消费者。
- 指出 Outbox Pending 也是队列前的积压，不能只看 Kafka Lag。

### 3:40–4:30 重试和 DLQ

- 点击“失败 3 次 → DLQ”，再从客户端提交异步订单。
- 消息记录三次 Attempt 后进入 DEAD_LETTER，业务执行次数为 0。
- 清除故障并“人工回放 DLQ”，订单最终成功且业务执行一次。

### 4:30–5:00 支付最终一致性

- 对异步产生的订单执行“支付但丢回调”。
- 支付表成功、订单暂时待支付，Job Runner 对账后变 PAID。
- 总结：Kafka 是通信策略；幂等、补偿与对账是一致性策略。

## 高频追问

**为什么不是 Kafka exactly-once？**

端到端还包含 MySQL 和 HTTP 下游，不能靠 Broker 配置消除所有重复窗口。本项目明确采用至少一次投递加业务幂等，证据是重复消息被收到但订单只执行一次。

**Outbox 会不会重复发？**

会。Broker 已确认但 PUBLISHED 尚未落库时宕机会重发。这正是消费者幂等不能省略的原因。

**库存不足为什么不重试？**

它是业务拒绝，不是瞬时技术错误。盲目重试浪费资源并扩大积压；只有超时、连接失败等技术异常进入有限重试。

**Lag 为零是否代表业务正确？**

不代表。只代表 Consumer Group 已提交到日志末尾，还要核对请求终态、订单、库存、支付、DLQ 和 Trace。

**为什么不用 XA？**

面试前选择可完整证明的 Kafka 链路。XA 适合短、内部可控且强一致需求高的事务，但支付等外部长事务更适合幂等和最终一致。本版本只讨论 XA，不声称实现。

## 压测怎么讲

两组 k6 脚本都采用 40 秒阶梯加压：前 10 秒逐步升到 5 VU，中间 20 秒升到 20 VU，最后 10 秒降到 0；每个 VU 会循环发请求，因此 20 VU 不等于总共 20 个请求。

| 口径 | 同步完整订单 | Kafka 异步受理 |
|---|---:|---:|
| 成功代表 | 订单、库存、支付和 Trace 完成 | request 与 Outbox 落库并返回 HTTP 202 |
| 请求数 | 1,804 | 4,254 |
| 吞吐 | 45.04 req/s | 106.18 req/s |
| P50 | 139.00ms | 33.31ms |
| P95 | 286.99ms | 56.12ms |
| P99 | 344.64ms | 83.05ms |
| HTTP 错误率 | 0% | 0% |

正确结论：异步入口更快完成“可靠受理”，不是更快完成订单。4,254 条异步请求随后约 362 秒才全部收敛；Kafka 把峰值压力转化为可观察的排队时间，没有提高热点库存行锁的处理能力。

现场说法：

> 在同一台本机、相同 40 秒和最高 20 VU 下，同步完整链路 P95 为 286.99ms、45.04 req/s；异步入口只完成 request 与 Outbox 落库并返回 202，P95 为 56.12ms、106.18 req/s。两者成功语义不同，不能宣称订单吞吐提升 2.36 倍。异步的价值是快速可靠受理和削峰，最终还要等待 Outbox、Lag 归零并核对 4,254 条请求全部成功。

## 现场恢复

- 状态混乱：运行 `reset-demo.cmd`。
- Kafka 故障未清：运维台点“清除 Kafka 故障”和“恢复消费”。
- 页面未即时刷新：确认 WebSocket 状态，手动刷新仍会从数据库恢复事实。
- 全量回归统一运行 `verify-v0.3.1.cmd`。


## 演示口径

- Spring Boot 是构建三个 Java 后端服务的框架，不是数据库；MySQL 才是业务数据库。
- Outbox 为零代表当前没有待发布事件；已发布总数和数据库行证明历史发布。
- Job 数量不随普通订单增长，只随需要补偿或对账的异常链路增长。
- Lag 是 Kafka 物理消息进度，队列中是数据库逻辑请求数，两者可能短暂不一致。
- 恢复普通消费不会自动回放 DLQ；必须选择具体死信后人工回放。
