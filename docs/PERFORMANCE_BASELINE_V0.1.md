# Bill System k6 性能基线 v0.1

测试日期：2026-09-13  
结论：本地单实例基线通过预设阈值，可证明已完成一次有明确负载模型的压测；不可外推为生产容量。

## 测试环境

| 项目 | 配置 |
|---|---|
| CPU | AMD Ryzen 7 5800H，8 核 16 线程 |
| 内存 | 15.9 GB |
| 操作系统 | Windows 11 + WSL2 + Docker Desktop |
| Docker Engine | 29.7.2 |
| 服务 | Order/Inventory/Payment 各 1 实例，MySQL 8.4、Redis 7.4 |
| 压测端 | `grafana/k6:0.54.0` 容器 |

## 负载模型

接口：`POST /api/orders`，每次使用唯一幂等键和 `LIFE-LOAD-001` 专用商品，包含订单落库、库存预占、支付单创建和 Trace 保存，不是空接口。

```text
0–10 秒：0 → 5 VU
10–30 秒：5 → 20 VU
30–40 秒：20 → 0 VU
每个 VU 每轮请求后停 50 ms
```

阈值：错误率 `< 5%`、P50 `< 250 ms`、P95 `< 800 ms`、P99 `< 1500 ms`。

## 结果

| 指标 | 结果 |
|---|---:|
| 请求/迭代 | 1804 |
| 业务检查通过率 | 100% |
| HTTP 错误率 | 0% |
| 吞吐 | 45.04 req/s |
| 平均延迟 | 155.12 ms |
| P50 | 139.00 ms |
| P90 | 272.14 ms |
| P95 | 286.99 ms |
| P99 | 344.64 ms |
| 最大延迟 | 366.53 ms |

全部阈值通过。

压测使用独立 SKU。报告保存后运行 `cleanup-load-data.cmd`，只删除 `LIFE-LOAD-001` 的压测订单、支付单、库存预占和 Trace，不影响人工演示订单。

## 解读

P50 表示一半请求在 139 ms 内完成；P95 表示 95% 请求在 286.99 ms 内完成；P99 更关注长尾，99% 请求在 344.64 ms 内完成。本轮随 VU 上升，吞吐稳定在本机约 45 req/s，未出现 HTTP 或业务检查失败。

这组数字只描述本次环境和数据。样本时间仅 40 秒，服务均为单实例，数据库和压测端也在同一台机器；没有覆盖长稳、资源瓶颈、多实例扩容、网络抖动或真实支付。因此面试中应称为“本地基线压测”，不能称为系统极限或线上 SLA。
