# Bill System 面试演示稿

## 三分钟主线

“我做的不是一个普通商城，而是一个生活服务交易可靠性实验台。系统拆成订单、库存、支付三个 Spring Boot 服务，前端通过订单服务编排，MySQL 三个独立 Schema，Redis 用于入口限流。”

第一步创建订单并连续重放相同请求。解释三层幂等：请求指纹防止同键换参数、按键加锁处理单实例竞态、数据库唯一索引兜底。自动测试里 20 个并发同键请求全部返回同一个订单 ID。

第二步点“支付但丢回调”。支付服务已经是成功事实，但订单仍显示 `PENDING_PAYMENT`。三秒后持久化 Job Runner 主动查询并恢复为 `PAID`，Trace 中能看到 `payment.succeed → payment.reconcile → payment.callback`。这体现的是最终一致性，不是假装分布式事务。

第三步展示任务中心和故障测试。支付查询连续失败三次后任务进入 `DEAD_LETTER`，恢复故障后人工重跑成功；支付服务连续故障会打开 Resilience4j 熔断器，后续调用快速失败，并由库存释放补偿收尾。

最后双击 `verify.cmd`：“这不是我口头描述的能力，九类场景都有可重复自动验收。”

## 高频追问

### 为什么不用分布式事务？

生活服务订单跨库存和支付，强行做两阶段提交会增加耦合和可用性风险。Demo 选择本地事务保存各服务事实，状态机保证合法推进，幂等接口允许重试，补偿和主动对账解决部分失败，接受短暂中间状态换取可用性。

### `synchronized` 能解决幂等吗？

不能单独解决。早期实现把 `synchronized` 放在带事务注解的方法上，事务代理先开事务再等待锁，并发下仍出现一次唯一键异常。修正后是按幂等键加细粒度锁，再在锁内开启事务，数据库唯一索引仍做最终兜底。多实例不能依赖 JVM 锁。

### 悲观锁会不会慢？

会增加热点行等待，所以只适合这个小型 Demo 和强竞争库存。生产会根据流量选择带库存条件的原子更新、分段库存、Redis 预扣或队列串行化，并用压测验证吞吐和一致性。

### 为什么支付成功却不直接把订单改成功？

支付服务和订单服务各自保存事实，网络回调可能丢失。支付成功不是“回调成功”。订单通过幂等回调或主动对账收敛，避免把一次网络失败误判成支付失败。

### P95 在哪里？能说做了压测吗？

可以说“完成了一轮本地基线压测”，但紧跟边界：40 秒阶梯加压、最高 20 VU、1804 个完整下单请求、约 45.04 req/s、错误率 0%，P50 139 ms、P95 286.99 ms、P99 344.64 ms。机器是 Ryzen 7 5800H、16 GB 内存、Docker 单实例。不能把它说成生产容量，也不能省略负载模型和环境。

### Trace 是不是 OpenTelemetry？

当前是自建业务 Trace Event，能把订单、支付、对账和补偿串起来，但不是完整 OTel Span。生产版会接 OpenTelemetry/Jaeger，并对用户标识、Token、请求正文做脱敏。

## 现场顺序

1. 练习前先运行 `reset-demo.cmd`，再双击 `start.cmd`，确认六个容器健康并打开控制台。
2. 创建订单，重放相同请求。
3. 支付但丢回调，先说明中间态，再等待自动恢复。
4. 展示 Trace 和 Job 列表。
5. 有时间再演示取消/退款。
6. 终端运行 `verify.cmd` 展示自动证据。

不要现场首次拉取镜像；面试前保持 Docker Desktop 已启动并预热一次 `start.cmd`。
