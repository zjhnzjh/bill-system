## 1. 项目定位

Bill System 是一个面向生活服务交易场景的订单可靠性与测试演示平台。它不是普通商城，也不重复 KUN 的 RAG/AI 评测能力，而是集中证明以下能力：

- 理解订单、库存、支付、取消和退款的完整交易链路；
- 处理重复请求、并发争抢、超时、部分失败和最终一致性；
- 建立接口自动化、Web 自动化和性能测试；
- 通过 Trace、任务中心和故障注入定位跨服务问题；
- 用可操作的前端界面展示可靠性机制，而不是只展示架构图；
- 明确区分本地 Demo、自动测试证据与生产能力。

## 2. 技术选型

| 层级 | 选型 | 说明 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 交易控制台、订单详情、故障实验室、Trace 与任务中心 |
| 后端 | Java 21 + Spring Boot 3.x | 三个独立微服务 |
| 数据库 | MySQL 8 | 单容器、三个独立 Schema，服务间禁止跨库直读 |
| 缓存与队列 | Redis 7 | 缓存、限流、削峰和异步任务辅助 |
| 容错 | Resilience4j | 超时、重试、熔断、隔离和降级 |
| 可观测性 | OpenTelemetry + Jaeger | Trace ID 传播与跨服务 Span；若工期受阻则先实现内置 Trace 页面 |
| 接口测试 | JUnit 5、Spring Boot Test、REST Assured | 正常、异常、幂等和状态机覆盖 |
| Web 测试 | Playwright | 至少覆盖一条完整交易链路和一个故障恢复场景 |
| 性能测试 | k6 | 阶梯加压、并发库存与 P50/P95/P99 |
| 运行方式 | Docker Compose + `start.cmd` | 全栈一键启动，固定端口，健康检查后打开浏览器 |

## 3. 系统结构

```text
React Web Console :3100
          │
          ▼
Order Service / BFF :8785
     │               │
     ▼               ▼
Inventory Service   Payment Service
     │               │
     └───────┬───────┘
             ▼
       MySQL + Redis
             │
             ▼
 Outbox / Job Runner / Trace
```

### 3.1 Order Service

- 创建、查询和取消订单；
- 校验并持久化幂等键；
- 保存价格快照；
- 执行订单状态机；
- 记录 Outbox 事件；
- 执行 Job Runner、补偿和人工恢复；
- 作为前端 BFF，避免前端直接编排交易一致性。

### 3.2 Inventory Service

- 查询库存；
- 预占、确认扣减和释放库存；
- 使用原子条件更新或版本号防止超卖；
- 对重复库存请求返回同一业务结果；
- 支持受控的超时、失败和延迟注入。

### 3.3 Payment Service

- 创建模拟支付单；
- 模拟支付成功或失败；
- 发送异步支付回调；
- 模拟重复回调和回调丢失；
- 提供支付结果主动查询；
- 支持退款与退款状态查询。

## 4. 核心交易链路

```text
创建订单
→ 校验参数与幂等键
→ 保存待确认订单
→ 预占库存
→ 固化价格快照
→ 进入待支付
→ 模拟支付
→ 接收或主动查询支付结果
→ 更新为支付成功
→ 履约完成
```

建议订单状态：

```text
CREATED
→ STOCK_RESERVED
→ PENDING_PAYMENT
→ PAID
→ FULFILLED

取消与退款：
CANCEL_PENDING
→ CANCELLED
→ REFUND_PENDING
→ REFUNDED

异常终态：
FAILED / MANUAL_REVIEW
```

所有状态变化必须校验当前状态和目标状态，不能由回调直接覆盖任意状态。

## 5. 九个可靠性演示场景

| 编号 | 场景 | 预期结果 | 技术点 | 优先级 |
|---:|---|---|---|---|
| 1 | 连续五次提交同一订单 | 只产生一个订单并复用首次结果 | 幂等键、唯一索引 | P0 |
| 2 | 多请求争抢最后一份库存 | 最多一个请求成功，不出现负库存 | 原子扣减、防超卖 | P0 |
| 3 | 库存服务超时或扣减失败 | 订单不进入待支付，状态可解释、可恢复 | 超时边界、重试、补偿 | P0 |
| 4 | 支付成功但回调丢失 | 定时对账主动发现并恢复订单状态 | Job Runner、最终一致性 | P0 |
| 5 | 支付平台重复发送回调 | 订单只推进一次，不重复记账 | 回调幂等、状态机 | P1 |
| 6 | 取消订单或支付后退款 | 正确释放库存或进入退款补偿 | Saga 式补偿 | P1 |
| 7 | 后台任务连续失败 | 指数退避，超限进入死信，可人工重跑 | 任务恢复、幂等执行 | P0 |
| 8 | 瞬时高并发下单 | 超限请求被明确拒绝或排队，系统不被打垮 | 限流、削峰、P50/P95 | P1 |
| 9 | 支付服务整体不可用 | 快速失败、隔离资源、展示降级并可恢复 | 熔断、降级、隔离 | P2 |

缓存一致性作为横向能力实现：Cache Aside、数据库提交后失效缓存、短 TTL、空值缓存、热点互斥和 TTL 抖动。

## 8. 启动与端口

用户日常只运行：

```text
D:\myproject\bill system\start.cmd
```

`start.cmd` 的目标行为：

1. 检查 Docker Engine；
2. 检查固定端口；
3. 使用 Docker Compose 启动前端、三个微服务、MySQL、Redis和可观测组件；
4. 等待健康检查；
5. 自动打开 `http://127.0.0.1:3100`；
6. 重复启动时识别同一项目实例；
7. 发现其他进程占用端口时明确失败，不自动漂移、不误杀进程。

### 10.1 环境结论

当前硬件和基础软件能够承载 Bill System，但还不能直接判定为“开发环境完全就绪”：Docker 已安装、WSL2 已配置，但 Docker Engine 当前没有运行。

全 Docker 模式下，本机没有 Java/Maven 不会阻塞项目启动，因为编译和运行可以发生在容器内；代价是首次下载镜像和 Maven 依赖较慢，日常修改后的重建速度也慢于本机 JDK。为了降低面试现场风险，项目镜像必须提前构建并缓存，不能把首次拉取镜像留到演示当天。

建议运行预算：

- Docker 可用内存控制在约 6–8GB；
- 开发和演示时关闭不需要的 KUN/Aikun 服务、浏览器标签和大型应用；
- MySQL、Redis、Jaeger、三个 Spring Boot 服务与前端预计占用约 4–7GB；
- 若实际内存压力过高，Jaeger 作为第一个可降级组件，内置 Trace 页面仍必须保留。
