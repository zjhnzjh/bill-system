## 本轮发现并修复的 Bad Case

### 1. 控制器方法签名冲突

原因：Trace 查询端点和 Trace ID 辅助函数同名同参数，Java 编译失败。  
修复：辅助函数更名为 `resolveTraceId`。  
经验：端点控制器也必须通过真实生产构建，而不能只凭编辑器判断。

### 2. 支付接口返回旧状态

原因：`pay()` 事务中的 JPA 一级缓存返回回调前加载的订单，数据库已成功但 API 仍返回待支付。  
修复：缩小事务边界，让回调提交后重新查询订单。  
经验：验证接口行为，不只验证数据库最终值。

### 3. 并发幂等偶发唯一键异常

原因：事务代理先于方法级 `synchronized` 开启事务，并发事务快照与锁边界不一致。  
修复：按幂等键加细粒度锁，在锁内显式开启事务，唯一索引捕获跨实例竞态。  
经验：AOP 代理顺序会改变你以为的临界区，幂等必须做并发验收。

### 4. Job 失败状态可能被整体事务回滚

原因：调度扫描与任务执行共用事务，内部失败即使被捕获，也可能把外层事务标记为 rollback-only。  
修复：扫描不包长事务，每个业务动作独立提交，任务成功或失败状态另行保存。  
经验：恢复任务必须保证“业务失败时，失败记录本身仍能提交”。

## 证据强度与边界

证据强度：本机真实服务集成测试 + HTTP 并发测试 + 故障注入，强于单元测试或设计文档；弱于多实例、长时间稳定性和生产流量验证。

适用边界：Windows 11、Docker Desktop、单 Order Service 实例、模拟支付、固定测试商品。不能据此宣称生产可用、真实支付安全或完成正式容量压测。
