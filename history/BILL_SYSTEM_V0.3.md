# Bill System v0.3 目标规划

状态：规划冻结候选，本文是 v0.3 的目标范围、技术边界与验收基准  
规划日期：2026-09-13  
员工编号：`MYPROJECT-GPT5-001`  
目标岗位：字节跳动中国交易与广告——生活服务商业平台全栈开发方向

## 1. 版本定位

Bill System v0.3 是一个面向面试展示的生活服务交易可靠性实验平台。它不追求把技术名词堆在架构图中，而是要求每项关键机制都满足以下条件：

1. 有真实运行的服务、数据库或基础设施参与；
2. 有可操作的正常、异常和恢复场景；
3. 有实时可视化过程，不只展示最终结果；
4. 有数据库、消息、Trace、事务日志或自动测试证据；
5. 能解释为什么使用、解决什么问题、付出什么代价；
6. 明确区分本地模拟能力、自动验收事实与生产能力。

v0.3 在 v0.2 的三服务、三页面、真实 MySQL、WebSocket、幂等、并发库存、支付恢复、熔断和压测基线之上，新增四条核心展示主线：

- **同步交易链路**：通过 HTTP 完成普通下单，展示低复杂度和即时结果；
- **Kafka 异步削峰链路**：通过 Outbox、Kafka、幂等消费者和死信处理高峰请求；
- **强一致事务链路**：通过 Seata XA 展示订单库与库存库的两阶段提交和整体回滚；
- **最终一致性链路**：支付不加入 XA，通过回调、消息、恢复任务和对账最终收敛。

核心面试结论：

> 同一个交易系统不会只使用一种一致性或通信方案。短时间、内部可控且必须同时成功的订单与库存操作可以演示 XA 强一致；涉及外部支付和长流程的部分使用最终一致性；普通流量可以同步处理，高峰流量可以通过 Kafka 削峰。所有路径都必须可观察、可验证、可恢复。

## 2. v0.3 架构决策摘要

| 决策 | v0.3 选择 | 原因与边界 |
|---|---|---|
| 浏览器入口 | 单一公开入口 `127.0.0.1:3100` | 三个页面同源，统一代理 HTTP 与 WebSocket，避免跨域和端口暴露 |
| 页面数量 | 保留客户端、服务端运维台、数据一致性控制台三页 | 三种观察角色不同，现有页面已形成清晰展示结构 |
| 后端服务 | Order、Inventory、Payment 三个独立进程 | 展示领域边界、独立数据所有权和跨服务故障 |
| 普通下单 | 同步 HTTP | 立即返回业务结果，结构清晰，适合常规流量 |
| 高峰下单 | Outbox + Kafka 异步处理 | 削平瞬时流量，保护下游，接受排队延迟 |
| 内部强一致 | Seata XA，仅覆盖订单与库存实验链路 | 真实展示 Prepare、Commit、Rollback 与锁代价 |
| 支付一致性 | 最终一致性 | 外部支付无法加入本地 XA，必须依赖回调、幂等、重试和对账 |
| 消息语义 | 至少一次投递 + 消费端幂等 | 不宣传不可信的端到端 Exactly Once |
| 实时页面同步 | WebSocket | 同一连接支持订阅、心跳、重连、事件序号和服务端推送 |
| 数据库页面 | 保留并升级 | 用作真实数据证据、一致性检测、事故注入、受控修复和审计，不提供任意 SQL |
| 性能证明 | 同一组 k6 负载对比同步与异步模式 | 区分接入延迟、排队时间、处理时间和最终完成时间 |

## 3. 系统拓扑与进程边界

### 3.1 单入口、多进程

面试官和浏览器只访问一个入口：

```text
http://127.0.0.1:3100/client
http://127.0.0.1:3100/operations
http://127.0.0.1:3100/database
```

单一端口不代表单进程。v0.3 通过 Web 容器或反向代理按路径把请求转发给多个内部进程：

```text
Browser :3100
  ├─ /client、/operations、/database → React SPA
  ├─ /api/orders/**                  → Order Service :8785
  ├─ /api/inventory/**               → Inventory Service :8786
  ├─ /api/payments/**                → Payment Service :8787
  └─ /ws/events                      → WebSocket endpoint

Internal infrastructure
  ├─ MySQL 8：bill_order / bill_inventory / bill_payment
  ├─ Redis 7：限流与必要的短期协调状态
  ├─ Kafka：异步命令、领域事件、重试与死信
  └─ Seata Server：XA 全局事务协调者
```

### 3.2 服务数据所有权

- Order Service 只能写 `bill_order`；
- Inventory Service 只能写 `bill_inventory`；
- Payment Service 只能写 `bill_payment`；
- 服务之间不得通过跨 Schema SQL 协作；
- 数据一致性控制台的正常修复必须调用所属服务的 Admin API；
- 只有明确标记的演示事故注入可以制造异常事实，且必须记录审计；
- Kafka、Seata、WebSocket 均不能成为业务最终状态的唯一来源，最终事实仍落在数据库中。

## 4. 三个界面

三个页面继续沿用 v0.2 的统一视觉和左侧导航。v0.3 面向面试官，允许直接展示 Kafka、Topic、Partition、Offset、XID、Trace ID、WebSocket Event ID 等技术证据。

### 4.1 客户端 `/client`

客户端同时展示业务体验和工程证据。

#### 业务区域

- 商品、价格、可用库存、已预占库存；
- 普通同步下单；
- Kafka 高峰异步下单；
- 正常支付、支付成功但回调丢失；
- 取消、释放库存、退款；
- 订单状态时间线；
- 异步请求状态：`ACCEPTED → QUEUED → PROCESSING → SUCCEEDED/REJECTED/FAILED`；
- WebSocket 断线、重连和最后同步时间。

#### 面试技术证据区域

每笔请求可展开显示：

- 交易模式：`SYNC_HTTP`、`KAFKA_ASYNC` 或 `XA_STRONG`；
- 请求 ID、订单 ID、幂等键、Trace ID；
- Kafka Topic、Partition、Offset、Message Key、Consumer Group；
- 消息生产时间、排队时间、消费开始时间、业务处理时间和端到端时间；
- WebSocket 事件类型、事件 ID、事件序号和推送时间；
- XA 场景中的 XID、分支事务和最终状态；
- 最终结果来自哪个公开查询接口。

客户端不得直接调用 Inventory/Payment 的写接口，也不得直接修改数据库。

### 4.2 服务端运维台 `/operations`

服务端运维台是 v0.3 的主要技术展示页面，分为以下区域或页内标签。

#### 服务拓扑

- Order、Inventory、Payment、Kafka、Seata、MySQL、Redis 的实时健康状态；
- 浏览器入口端口和各内部进程端口；
- 当前 WebSocket 连接数、订阅数和最近事件；
- 当前同步请求数、Kafka 积压和恢复任务数。

#### 交易链路

- 按请求 ID、订单 ID、Trace ID、XID 搜索；
- 关联订单、库存预占、支付、Outbox、Kafka 消息、Job 和审计记录；
- 展示每一步的服务、动作、结果、耗时与错误；
- 同一订单的业务状态时间线与技术事件时间线对齐。

#### XA 事务观察器

- 全局事务 XID 和当前状态；
- Order、Inventory 分支事务 ID；
- 第一阶段 Prepare 的开始、结束和投票结果；
- 第二阶段 Commit 或 Rollback；
- 锁持有时间、全局事务耗时、失败位置；
- 正常提交、分支失败、协调延迟三种实验；
- 数据库提交或回滚后的真实数据对比。

#### Kafka 流量与消息

- Topic、Partition、Consumer Group；
- 实时生产速率、消费速率和积压量；
- 当前 Offset、消费 Lag 和最老消息等待时间；
- 消费者实例数、并发度、处理上限和健康状态；
- 成功、库存不足、业务失败、技术失败数量；
- 重试次数、重试 Topic、死信 Topic；
- 重复消息数和被幂等机制拦截的数量；
- 高峰结束后积压清空过程；
- 单条消息从请求受理到最终订单结果的完整链路。

#### 压测对比

- 同步 HTTP 和 Kafka 异步模式使用相同输入负载；
- 实时展示输入速率、处理速率、错误率、P50/P95/P99；
- 异步模式单独展示接入延迟、队列等待、业务处理和最终完成延迟；
- 展示服务 CPU、内存、线程池、连接池及 Kafka Lag；
- 明确标注本地环境、脚本版本、代码版本、数据规模与阈值；
- 不把 HTTP `202 Accepted` 误算为订单创建成功。

#### 故障与恢复

- 库存失败、库存延迟；
- 支付失败、支付超时、回调丢失、重复回调；
- Kafka 消费暂停、消费异常、重复投递；
- XA 分支失败、第二阶段延迟；
- WebSocket 主动断开；
- Job Runner 重试、死信和人工重跑；
- Resilience4j 熔断器、隔离和恢复状态；
- 一键清除所有故障，但不得清除审计证据。

### 4.3 数据一致性控制台 `/database`

v0.2 的“数据库操作台”升级为“数据一致性控制台”。页面仍显示真实 MySQL 数据，但明确区分观察、事故注入和修复。

#### 真实数据证据

- 分 Schema 展示 `orders`、`order_requests`、`outbox_events`；
- 展示 `inventory_items`、`inventory_reservations`；
- 展示 `payments`、`recovery_jobs`；
- 展示 Kafka 消息索引、XA 事务证据和审计记录；
- 表格标明所属服务、Schema、表名、记录数和最后更新时间；
- 支持按订单 ID、请求 ID、幂等键、Trace ID、XID 查询；
- 默认只读，不提供任意 SQL 输入框。

#### 一致性检测

自动识别但不自动篡改以下异常：

- 支付为 `SUCCEEDED`，订单仍为 `PENDING_PAYMENT`；
- 订单已取消但库存预占仍有效；
- 库存可用量或预占量小于零；
- 同一订单存在多个有效库存预占；
- 相同幂等键产生多个业务订单；
- Outbox 长时间未发布；
- Kafka 消息已消费但业务结果缺失；
- 恢复任务超过最大重试次数；
- XA 已结束但业务数据与预期不符。

每条异常必须展示严重程度、检测规则、涉及记录、可能原因和建议动作。

#### 事故注入

- 设置演示商品库存为 `0`、`1`、`10` 或自定义非负数；
- 在没有有效预占时删除并恢复演示商品；
- 受控推进模拟支付事实；
- 暂停指定 Kafka 消费者；
- 制造一次 Kafka 消费失败或重复投递；
- 制造一次 XA 库存分支失败或协调延迟；
- 所有按钮标注“仅限本地演示环境”；
- 所有操作记录操作者、原因、前值、后值、时间、Trace ID。

#### 受控修复

受控修复采用以下流程：

```text
发现异常
→ 展示检测证据
→ 生成修复计划
→ 用户确认
→ 调用所属服务 Admin API
→ 展示修改前后 Diff
→ 写入审计记录
→ 再次运行一致性校验
```

支持主动对账、重发 Outbox、重试死信消息、释放孤立预占、重跑恢复任务。不得提供无边界删除、系统表修改或任意 SQL。

## 5. 三种订单处理模式

### 5.1 `SYNC_HTTP`：普通同步下单

```text
Client
→ Order Service 创建待确认订单
→ Inventory Service 本地事务预占库存
→ Order Service 创建支付单并进入待支付
→ 返回最终创建结果
```

特点：

- 调用链直观，结果立即返回；
- 适合普通流量和需要同步结果的场景；
- 下游延迟会直接增加客户端延迟；
- 下游故障可能占用调用线程和连接；
- 通过超时、重试边界、熔断和补偿提高可靠性。

### 5.2 `KAFKA_ASYNC`：高峰异步下单

```text
Client
→ Order Service 接受异步请求
→ 同一本地事务写 order_requests 与 outbox_events
→ 返回 HTTP 202 + requestId
→ Outbox Relay 发布 order-create-command
→ Kafka Consumer 幂等消费
→ 创建订单并预占库存
→ 发布或记录最终结果
→ WebSocket 推送客户端
→ 客户端通过查询接口确认最终事实
```

关键规则：

- `202 Accepted` 只代表请求可靠受理，不代表订单创建成功；
- `requestId` 与幂等键全局唯一；
- Outbox 与请求登记必须在同一数据库本地事务中写入；
- Relay 重复发布是允许的，消费者必须幂等；
- Kafka 使用至少一次投递语义；
- 消费失败按策略进入重试 Topic，超限进入死信 Topic；
- 库存不足属于业务拒绝，不进入技术重试；
- Kafka 只削平瞬时流量，不增加系统真实处理能力；
- 队列积压必须有上限、告警和拒绝策略。

### 5.3 `XA_STRONG`：订单与库存强一致实验

Seata XA 只覆盖 Order 与 Inventory 的短事务实验，不覆盖支付：

```text
Order Service 开启全局事务 XID
→ Order 分支写入订单库并 Prepare
→ Inventory 分支扣减库存并 Prepare
→ 所有分支成功：统一 Commit
→ 任一分支失败：统一 Rollback
→ XA 完成后再进入支付流程
```

必须展示：

- 协调者、全局事务和分支事务的关系；
- 第一阶段 Prepare 和第二阶段 Commit/Rollback；
- 分支失败后的整体回滚；
- 第二阶段延迟时的锁等待和吞吐影响；
- 为什么支付不参加 XA；
- XA 强一致与最终一致性的适用范围和代价。

## 6. Kafka 设计

### 6.1 Topic 与消费组

建议最小 Topic 集合：

| Topic | 用途 | Key | 消费组 |
|---|---|---|---|
| `order-create-command` | 异步创建订单命令 | `requestId` | `order-create-v1` |
| `order-create-retry` | 可重试技术失败 | `requestId` | `order-create-retry-v1` |
| `order-create-dlq` | 超过重试上限的消息 | `requestId` | 人工处理 |
| `order-status-event` | 订单状态变化事件 | `orderId` | WebSocket/观察器 |
| `payment-status-event` | 模拟支付事实变化 | `paymentId` | Order 恢复处理器 |

Topic、分区数和保留时间必须在配置文件中固定并记录，不在面试现场临时创建漂移配置。

### 6.2 幂等与重复消费

- 消费者以 `messageId` 或 `requestId` 建立数据库唯一约束；
- 消息处理结果持久化后才提交 Offset；
- 业务处理成功但 Offset 提交失败时允许再次收到同一消息；
- 重复消息返回首次处理结果，不重复创建订单或扣减库存；
- 页面展示“收到次数”和“实际执行业务次数”；
- 不以 Kafka 的宣传性 Exactly Once 替代业务幂等。

### 6.3 重试与死信

- 网络超时、临时数据库异常等技术故障允许重试；
- 参数错误、商品不存在、库存不足等业务结果不得无意义重试；
- 重试采用有上限的退避策略；
- 超限消息进入 `order-create-dlq`；
- 人工重放前必须展示原始错误、历史尝试和幂等状态；
- 人工重放仍走相同幂等处理器。

### 6.4 积压保护

- 设定最大可接受 Lag 或最老消息等待时间；
- 超过阈值时运维台告警；
- 达到硬上限后新请求返回明确的过载响应，不无限排队；
- 客户端显示“系统繁忙，请稍后再试”，并保留请求是否已受理的明确证据；
- Kafka 恢复后展示积压排空过程。

## 7. XA 两阶段事务设计

### 7.1 参与者

- Seata Server：全局事务协调者；
- Order Service：订单分支；
- Inventory Service：库存分支；
- MySQL：支持 XA 的资源管理器；
- Payment Service：明确不参与 XA。

### 7.2 正常提交场景

1. Order Service 创建 XID；
2. Order 分支写入订单并进入 Prepared；
3. Inventory 分支原子扣减并创建预占，进入 Prepared；
4. 两个分支都成功后，协调者发出 Commit；
5. 数据库页显示订单存在、库存减少、预占存在；
6. 运维台显示完整阶段、耗时和最终状态 `COMMITTED`。

### 7.3 分支失败回滚场景

1. Order 分支 Prepare 成功；
2. Inventory 分支注入失败；
3. 协调者发出 Rollback；
4. 订单记录不得残留；
5. 库存不得减少，预占不得存在；
6. 运维台显示失败分支、回滚阶段和最终状态 `ROLLED_BACK`。

### 7.4 协调延迟与锁代价场景

1. 两个分支进入 Prepared；
2. 故意延迟第二阶段；
3. 发起另一个竞争同一库存的请求；
4. 展示锁等待、请求延迟和吞吐下降；
5. 恢复协调后完成提交或回滚；
6. 明确证明 XA 的强一致性以可用性和性能为代价。

### 7.5 明确边界

- XA 只用于教学和对比所需的短内部链路；
- 不把用户支付、人工等待或外部机构调用包含在长事务中；
- 不声称 XA 是所有交易系统的默认最佳方案；
- XA 协调者故障恢复必须依赖真实事务日志，不允许只修改前端状态；
- 如果实际实现无法取得可靠的 Seata 阶段数据，页面不得伪造 Prepare/Commit 证据。

## 8. 支付最终一致性

支付链路继续证明真实交易系统必须处理的短暂不一致。

### 8.1 支付成功但回调丢失

```text
Payment Service 本地事务写 SUCCEEDED
→ 回调被故障开关丢弃
→ Order 保持 PENDING_PAYMENT
→ recovery_jobs 写入真实任务
→ Job Runner 或对账处理器查询支付事实
→ 幂等推进 Order 为 PAID
→ WebSocket 推送三个页面刷新
```

### 8.2 Kafka 支付事件重复

- 同一 `payment-status-event` 可重复投递；
- Order Service 按 `eventId` 和订单状态机幂等处理；
- 第一次推进订单，后续重复事件记录为 `DUPLICATE_IGNORED`；
- 不重复记账、不重复扣库存、不重复生成恢复任务。

### 8.3 主动对账

- 按订单或时间窗口扫描支付事实与订单状态；
- 只修复可证明的单向状态差异；
- 无法自动判断时进入 `MANUAL_REVIEW`；
- 自动修复与人工修复都记录原因和审计；
- 页面展示检测前、修复动作和修复后结果。

## 9. WebSocket 实时证据

WebSocket 不承担交易提交，只承担订阅和实时通知。

### 9.1 连接能力

- 连接 `/ws/events`；
- 客户端发送订阅命令，例如订阅指定 `requestId`、`orderId` 或运维事件；
- 服务端发送心跳，页面展示最近心跳；
- 断线采用有上限的退避重连；
- 重连时客户端提交最后收到的事件序号；
- 如果事件无法补发，客户端重新读取公开查询接口恢复真实状态。

### 9.2 事件信封

每条事件至少包含：

```text
eventId
sequence
eventType
aggregateType
aggregateId
occurredAt
traceId
payloadVersion
```

页面允许查看事件类型、序号、延迟和关联 Trace，但不得把 WebSocket 消息当作数据库事实。

### 9.3 断线恢复演示

1. 客户端订阅一个异步订单；
2. 主动断开 WebSocket；
3. Kafka Consumer 完成订单；
4. 客户端重连并提交最后事件序号；
5. 页面补收通知或重新查询；
6. 最终展示正确订单结果，证明断线不会丢失业务事实。

## 10. 核心业务不变量

所有事务模式必须共同满足：

- 可用库存和预占库存不得小于零；
- 同一订单、SKU 只能存在一个有效预占；
- 相同幂等键只能产生一个业务结果；
- 同一消息重复消费不得重复创建订单或重复扣减库存；
- 支付回调和支付事件重复到达不得重复推进订单；
- 非法订单状态转换必须拒绝；
- 取消、释放库存、退款、补偿和人工重跑必须可重复执行；
- `202 Accepted` 不等于订单成功；
- XA 回滚后不得残留订单、库存扣减或有效预占；
- 最终一致性任务超过重试上限后必须可见，不得静默丢失；
- 页面刷新、WebSocket 断线或前端重启不得改变业务事实。

## 11. 压测与削峰对比

### 11.1 公平对比原则

同步和异步两组测试必须使用：

- 相同机器和 Docker 资源预算；
- 相同商品、库存和请求数据分布；
- 相同输入到达率或 VU 阶梯；
- 相同测试时长和预热规则；
- 相同代码版本；
- 独立重置后的干净数据集；
- 固定并可追溯的 k6 脚本。

### 11.2 建议负载阶段

最终数值允许依据本机能力调整一次后冻结，文档和脚本必须一致：

```text
预热：10 VU，10 秒
爬升：10 → 50 VU，20 秒
高峰：50 VU，20 秒
突发：100 VU，10 秒
排空观察：停止生产后继续观察最多 60 秒
```

为了稳定制造可观察积压，可以在 Kafka 场景将消费者处理能力受控限制为固定速率；页面必须明确这是实验参数。

### 11.3 同步模式指标

- 完整创建订单的 P50/P95/P99；
- 吞吐量、HTTP 错误率、业务拒绝率；
- Order/Inventory/Payment 线程池使用；
- 数据库连接池使用与等待；
- 超时、熔断、限流数量；
- 库存是否超卖、幂等是否失效。

### 11.4 Kafka 模式指标

- 请求受理 P50/P95/P99；
- 从受理到最终结果的 P50/P95/P99；
- Kafka 生产速率、消费速率；
- Lag 峰值、最老消息等待时间；
- 队列等待时间与业务处理时间；
- 重试、死信、重复消费和幂等拦截；
- 高峰结束后的排空时间；
- 下游服务是否保持在受控负载范围。

### 11.5 结论边界

- Kafka 模式的低 HTTP 接入延迟不得与同步模式的完整业务延迟直接比较；
- Kafka 不会提升单个消费者的处理能力，只会缓冲和削平流量；
- 本地单机结果只构成回归基线，不代表生产容量或线上 SLA；
- 所有页面数字必须来自本次真实运行，不硬编码、不沿用不匹配的旧结果；
- 测试结果保存运行时间、环境、Git Commit、脚本哈希和原始输出。

2. 发起竞争相同库存的请求；

4. 恢复协调器并完成事务；
5. 说明强一致性的性能与可用性代价。

### 场景 H：支付回调丢失后最终恢复

### 场景 J：WebSocket 断线不丢业务结果

3. 后端继续完成订单；
4. 浏览器重连、补收或重新查询；
5. 最终状态正确且事件缺口可解释。
