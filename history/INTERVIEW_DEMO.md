# Bill System v0.2 面试演示手册

## 面试前准备

正确顺序：

1. 启动 Docker Desktop；
2. 双击 **start.cmd**，等待六个容器健康并自动打开客户端；
3. 双击 **reset-demo.cmd**，清空练习数据并恢复演示库存；
4. 依次打开客户端、服务端运维台、数据库操作台；
5. 面试前完成一次 **verify.cmd**，不要现场首次构建镜像或下载依赖。

三个页面：

- 客户端：http://127.0.0.1:3100/client
- 服务端运维台：http://127.0.0.1:3100/operations
- 数据库操作台：http://127.0.0.1:3100/database

## 五分钟主线

### 第 1 分钟：介绍系统

“我做的不是一个普通商城页面，而是一个生活服务交易可靠性实验台。系统有订单、库存、支付三个 Spring Boot 服务，各自拥有独立 MySQL Schema，Redis 负责入口限流。v0.2 又把展示分成客户端、服务端运维台和数据库操作台，三个页面通过 WebSocket 收到变更通知，但数据源始终是数据库。”

### 第 2 分钟：真实库存影响客户端

1. 在数据库操作台把演示商品库存设为 0；
2. 客户端实时显示售罄，但仍可点击“尝试下单并观察失败”；
3. 订单真实落库为 FAILED，库存不会变负数，也不会创建支付单；
4. 运维台 Trace 指向 inventory.reserve，并显示库存不足原因；
5. 数据库台出现 SET_AVAILABLE 审计记录。

讲法：“这里不是前端写死失败提示。我改变的是库存服务自己的 MySQL 数据，订单服务仍通过 HTTP 调用库存服务，失败状态、Trace 和审计都是真实产生的。”

### 第 3 分钟：跨库状态与最终一致性

1. 恢复库存并创建一个待支付订单；
2. 在数据库操作台把支付事实标记为 SUCCEEDED；
3. 指出支付表已成功，但订单仍是 PENDING_PAYMENT；
4. 到客户端点击“主动对账”；
5. 运维台展示 payment.reconcile，订单收敛为 PAID。

讲法：“支付服务和订单服务不能共享一个本地事务。系统保留短暂中间态，通过幂等回调或主动对账恢复最终一致，而不是跨库直接改订单。”

### 第 4 分钟：回调丢失与 Job Runner

1. 新建订单并点击“支付但丢回调”；
2. 支付表已经是 SUCCEEDED，订单暂时仍待支付；
3. recovery_jobs 中出现 PAYMENT_RECONCILE；
4. Job Runner 自动查询支付事实并把订单恢复为 PAID；
5. 三个页面通过 WebSocket 同步显示结果。

### 第 5 分钟：测试证据与压测边界

打开运维台“怎么验收压测”区域：

- 压测对象是完整创建订单链路，不是空接口；
- 40 秒阶梯加压，最高 20 VU；
- 1804 次请求，约 45.04 req/s，HTTP 失败率 0%；
- P50 为 139.00ms，P95 为 286.99ms，P99 为 344.64ms；
- 这是 Ryzen 7 5800H、16GB 内存、Docker 单实例的本地基线，不能外推生产容量。

最后说明：“verify.cmd 会回归 v0.1 九类可靠性场景，再执行 v0.2 三端联动验收。这些能力不只靠口头描述。”

## 高频追问

### 为什么不让后台直接执行 SQL？

任意 SQL 权限过大，会绕过业务校验，也无法稳定记录谁改了什么。v0.2 通过 Inventory 和 Payment Service 的受控 Admin API 操作，只允许有限状态推进、非负库存和安全删除，并追加审计记录。正式系统还应增加账号、RBAC 和审批；本地 Demo 明确不伪装成生产权限系统。

### WebSocket 是数据源吗？

不是。WebSocket 只推送“状态可能改变，请刷新”的通知。页面收到消息后重新读取 HTTP 查询接口，所以断线重连或浏览器刷新后仍以数据库为准，不会因为漏掉一条消息造成永久错误。

### 为什么支付成功后订单没有立即成功？

这是故意保留的跨服务事实差异。支付成功不等于回调一定到达，订单通过幂等回调或 Job Runner 主动查询支付事实后收敛，体现最终一致性。

### synchronized 能解决幂等吗？

不能单独解决。项目使用请求指纹、按幂等键细粒度锁和数据库唯一索引。JVM 锁只优化单实例并发，多实例仍依靠数据库约束或分布式协调。

### Trace 是 OpenTelemetry 吗？

当前是持久化业务 Trace Event，能关联订单、支付、对账和补偿，但不是完整的 OpenTelemetry Span。生产方向是接入 OpenTelemetry/Jaeger，并对用户标识、Token 和请求正文脱敏。

## 现场故障恢复

- 页面数据混乱：先确保服务运行，再双击 reset-demo.cmd；
- 按钮返回故障：在运维台点击“清除全部故障”和“复位熔断器”；
- 商品被删除：到数据库操作台点击“恢复演示商品”；
- 页面显示 WebSocket 重连：等待约 1.5 秒；HTTP 数据仍可刷新，不影响持久化事实；
- 端口冲突：start.cmd 会明确停止并给出占用端口，不会自动漂移或误杀进程。
